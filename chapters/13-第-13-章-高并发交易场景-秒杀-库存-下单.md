#### 13.1 【秒杀】100 万件库存、峰值 10 万 QPS，库存扣减怎么设计才不超卖？
> **难度**：L3 深入 ｜ **考察频次**：高 ｜ **目标能力**：架构权衡 ｜ **标签**：秒杀、库存扣减、分布式锁

**业务场景与约束**
- **业务背景**：电商大促单 SKU 限量秒杀，面向手机端普通消费者；超卖会直接产生资损并向客服爆发客诉；少卖最多损失部分 GMV，可接受。
- **量化约束**：单 SKU 100 万件库存；峰值 10 万 QPS；一致性要求为「零超卖、允许 0.5% 少卖」；下单 P99 < 300ms；基础设施为 Redis Cluster + MySQL 分库分表。

**渐进式追问**
1. 流量只有 100 QPS 时，单机能怎么保证扣减不超卖？
2. 流量放大到 10 万 QPS，直接让请求打进数据库 `UPDATE` 会崩在哪？
3. 为什么「先 `SELECT` 查库存再 `UPDATE` 扣减」在并发下一定超卖？
4. 既然超卖是因为并发，那加一把分布式锁为什么还是挡不住 10 万 QPS？
5. 用 Redis `Lua` 把库存扣减做成原子操作后，异步落库到 MySQL 失败了怎么办？
6. 业务允许 0.5% 少卖，那多扣（或扣了没卖出去）的库存怎么回收？
7. 若 Redis 与 MySQL 最终对不上，靠什么做最后兜底？

**参考答案要点**
主方案是「分层削峰 + Redis 原子扣减 + MQ 异步落库 + 数据库乐观锁兜底 + 对账补偿」五段式。削峰层先用答题/令牌桶/风控把 10 万 QPS 压到可接受量级；库存按段拆分到多个 `key`（如 `stock_00…stock_15`），用 `Lua` 脚本原子判断并扣减，避免单 `key` 热点；扣减成功后发 MQ 异步落库，MySQL 用 `UPDATE stock=stock-1 WHERE id=? AND stock>=1` 做乐观锁兜底，影响行数为 0 即视为已售罄。

为什么不选纯分布式锁：锁保护的是「单次操作互斥」，10 万 QPS 下要么锁竞争把 RT 打到秒级，要么退化成串行——锁解决不了量级，只解决正确性。为什么不选 `SELECT` 再 `UPDATE`：`SELECT` 读到的值在 `UPDATE` 前已被别的线程改掉，这是经典的不可重复读，必须让判断和扣减在同一行原子完成。

Redis 扣减成功但落库失败，靠「已扣不减回」+ 对账：Redis 是权威计数，落库失败只记失败流水，由定时任务补偿重试；少卖回收靠活动结束后的对账任务比对 Redis 与 MySQL，把未成交预占回收为可售。若 Redis 与 MySQL 严重偏离，以 MySQL 乐观锁结果为准——它才是零超卖的最后防线。

**可接受的关键结论**
- 零超卖的防线必须放在「判断与扣减原子」上，靠 `Lua` 或 `WHERE stock>=n` 实现，不能靠应用层 `SELECT+UPDATE`。
- 分布式锁解决正确性不解决量级，10 万 QPS 下它不是主方案。
- Redis 负责扛量、MySQL 乐观锁负责兜底，两者是「快路径 + 权威路径」关系。
- 落库失败不要回滚 Redis，用补偿对账回收少卖，保证零超卖优先于少卖回收。
- 活动结束后必须跑对账任务，否则 Redis 与 MySQL 的长期漂移无法自愈。

**考察意图**
这题验证候选人能不能从「写对一条 SQL」升级到「扛住一个量级的系统设计」。区分 L2 和 L3 的分水岭在：L2 会给出 Redis+锁的方案并认为安全；L3 能明确指出「锁挡不住量级」「扣减与判断必须原子」「落库失败用补偿而非回滚」这三句，并解释每一处的代价取舍。

**常见错误回答**
- ❌ 「加一把 `Redis` 分布式锁保证不超卖」—— 锁只互斥单次操作，10 万 QPS 下退化为串行或 RT 爆炸，挡不住量级。
- ❌ 「先查库存够不够，够就减」—— `SELECT` 与 `UPDATE` 之间有并发窗口，必然超卖，必须原子化。
- ❌ 「扣减成功落库失败就把 Redis 库存加回去」—— 回滚会引入超卖竞态，正确做法是记失败流水走补偿。
- ❌ 「用 `MySQL` 事务保证原子就行」—— 事务把单行锁住，10 万 QPS 直接把行锁和连接打满。
- ❌ 「库存不一致跑个定时任务就好了，不用设计」—— 没说清对账以谁为权威、少卖怎么回收，等于没兜底。

#### 13.2 【下单】库存该在下单时扣、支付时扣，还是先预占？
> **难度**：L1 入门 ｜ **考察频次**：高 ｜ **目标能力**：方案对比 ｜ **标签**：库存预占、下单、关单回滚

**业务场景与约束**
- **业务背景**：标准电商下单链路，用户从购物车提交订单；库存是稀缺资源，扣错时机要么丢单要么资损。
- **量化约束**：日均订单 50 万；支付转化率 70%；平均支付时长 3 分钟；下单后 15 分钟未支付自动关单释放库存。

**渐进式追问**
1. 下单时直接扣库存，会有什么问题？
2. 支付成功时才扣库存，用户下单后没库存了怎么办？
3. 什么叫「先预占、支付后确认、超时释放」的三态模型？
4. 三态模型里，15 分钟未支付怎么把库存放回去？
5. 关单回滚库存时重复关单会扣两次吗？怎么保证幂等？
6. 有人恶意下单占库存不付，怎么防？

**参考答案要点**
三种时机本质是「超卖风险 / 少卖风险 / 用户体验 / 实现复杂度」的取舍，给一张对比表：

| 时机 | 超卖风险 | 少卖风险 | 用户体验 | 复杂度 |
|------|---------|---------|---------|-------|
| 下单即扣 | 无 | 30% 未支付订单占着库存，等效少卖 | 好 | 低 |
| 支付即扣 | 高，支付瞬间库存可能已被占 | 无 | 差，易「下单成功却买不到」 | 低 |
| 先预占+确认 | 无 | 仅预占未支付这段窗口，少卖最小 | 好 | 中（需关单回滚） |

结论是选「预占」：下单时 `stock` 减库存、同时生成一条 `order` 状态为 `CREATED`；支付回调把状态置 `PAID` 即确认；关单任务在 15 分钟末把 `CREATED` 未支付单的库存加回。回滚必须幂等——用状态机 `CAS(CREATED→CLOSED)` 或乐观锁版本号，关单任务重复跑也只生效一次；恶意占库存靠单用户预占上限 + 风控降权。

**可接受的关键结论**
- 下单即扣体验好但有 30% 的「占而不付」少卖；支付即扣会超卖伤体验，一般不选。
- 预占三态（CREATED/PAID/CLOSED）是兼顾零超卖与少卖最小的折中。
- 关单回滚必须用状态机 CAS，不能先查状态再更新，否则重复关单会多放库存。
- 预占不是无限占，要配超时释放 + 单用户预占上限防恶意。

**考察意图**
这是本模块唯一的 L1 锚点，验证应届生是否理解「扣库存是一个带业务语义的状态问题」而非一句 SQL。分水岭在于：能不能张口就给出三态模型和那张对比表，并说出 70% 转化率下「下单即扣 = 30% 少卖」这种量化直觉。

**常见错误回答**
- ❌ 「支付时扣最安全，不会少卖」—— 忽略了支付瞬间别人已占库存导致的超卖和体验崩塌。
- ❌ 「下单即扣就行，简单」—— 没算过 30% 未支付订单等于把三成库存白白占 15 分钟。
- ❌ 「关单时查一下没支付就回库存」—— 先查后改有竞态，重复关单会多放，必须 CAS。
- ❌ 「库存回滚失败重试就行」—— 没说幂等，重试本身就是重复放库存的来源。
- ❌ 「预占不用释放，用户迟早会付」—— 真实场景有弃单和恶意占，不释放库存就锈死。

#### 13.3 【热点行】单 SKU 1 万 TPS 扣减，MySQL 行锁打满、CPU 飙升
> **难度**：L3 深入 ｜ **考察频次**：中 ｜ **目标能力**：瓶颈定位 ｜ **标签**：热点行、行锁、库存分桶

**业务场景与约束**
- **业务背景**：爆款单 SKU 被瞬时集中扣减，全表其他数据正常，只有这一行成为瓶颈。
- **量化约束**：MySQL 8.0；单表 2 亿行；热点集中在单行；事务 RT 从 5ms 涨到 300ms，CPU 打满。

**渐进式追问**
1. 明明只更新一行 `WHERE id=?`，为什么还会有锁等待和 CPU 飙升？
2. `UPDATE ... SET stock=stock-1 WHERE id=? AND stock>=1` 已经是行锁了，为什么仍然排队？
3. 把库存拆成 16 个子桶 `stock_00…stock_15` 随机路由，怎么扣、怎么合并？
4. 能不能用 Redis 前置把热点挡在数据库外面？
5. 批量合并提交（group commit）在这种场景怎么用？
6. 调 `innodb_thread_concurrency` 能解决吗？加索引或换隔离级别有用吗？

**参考答案要点**
先定位：单行热点下，所有 `UPDATE` 都要拿同一行的 `X` 锁，事务没提交前后来者只能排队；InnoDB 还要跑死锁检测（`innodb_deadlock_detect`），每笔都要和等待队列里的其他人比对，队列越长开销越大——RT 从 5ms 涨到 300ms、CPU 飙升正是这个排队 + 检测的开销，不是 SQL 慢。

注意「行锁」只保证互不覆盖，不保证不排队：1 万 TPS 抢同一行，等价于 1 万 个事务串行过这道门，单行就是天花板。解决思路按代价从低到高：① Redis 前置扣减，把 99% 请求挡在 DB 外，DB 只异步对账；② 库存分桶，逻辑库存拆 16 份 `stock_00…stock_15`，扣减时随机选桶 `WHERE bucket=? AND stock>=1`，把单行热点打散成 16 行，跨桶不足时再选第二个桶合并；③ group commit，把同桶短时间窗内的多次扣减合并成一次 `UPDATE`，降低单行写频率。

为什么加索引/换隔离级别基本没用：热点在「被更新那行」本身，索引只加速定位、隔离级别只影响读，都不减少写这一行的固有串行；`innodb_thread_concurrency` 限制并发进入 InnoDB 的线程数，调它能缓解线程风暴却换不来吞吐，是止血不是治病。

**可接受的关键结论**
- 行锁保证不互相覆盖，但不消除排队；单行热点本质是「写串行」，RT 与 CPU 暴涨来自队列 + 死锁检测开销。
- 根治靠把单行热点打散：Redis 前置 + 库存分桶（随机路由 + 跨桶合并）最有效。
- group commit 用「合并写」降低单行写频率，适合扣减可累积的场景。
- 加索引、换隔离级别、调 `innodb_thread_concurrency` 都治标不治本，别把时间花在这。

**考察意图**
验证候选人会不会「看到 CPU 高就无脑加索引/调参」。分水岭在：能否一针见血说出「行锁也会排队、死锁检测有开销、热点是写串行」，并给出分桶打散的具体实现，而不是甩一句「上缓存」。

**常见错误回答**
- ❌ 「加个索引让 `UPDATE` 更快」—— 热点在更新行本身，索引只帮定位，不减少写这一行的串行。
- ❌ 「把事务隔离级别调低就不锁了」—— 写永远要拿 X 锁，隔离级别只影响读，热点照旧。
- ❌ 「调大 `innodb_thread_concurrency` 提升并发」—— 这是限制进 InnoDB 的线程数，调大反而加剧排队风暴。
- ❌ 「直接上 Redis 就行，不用管 MySQL」—— 没说清 Redis 与 DB 如何对账、分桶合并怎么落地，等于甩名词。
- ❌ 「热点行用 `SELECT ... FOR UPDATE` 提前锁」—— 提前显式加锁只会把隐式排队变成长事务阻塞，更糟。
- ❌ 「分库分表就能解决」—— 单 SKU 无法按 id 再分，分表反而把热点集中到某分片的一行。

#### 13.4 【幂等】用户重复点击 + 网关重试导致重复下单
> **难度**：L2 进阶 ｜ **考察频次**：高 ｜ **目标能力**：边界处理 ｜ **标签**：幂等、令牌、唯一索引

**业务场景与约束**
- **业务背景**：弱网下用户狂点提交，叠加网关超时重试，同一笔意向订单可能被发多次。
- **量化约束**：网关超时重试最多 3 次；App 弱网可重发；订单表 5 亿行；下单峰值 3000 QPS。

**渐进式追问**
1. 为什么「先查有没有再插」不能保证不重复下单？
2. 幂等令牌怎么发、怎么校验、怎么消费？
3. 令牌校验和删除如果不是原子的会怎样？
4. 除了令牌，数据库还能做什么兜底？
5. 捕获 `DuplicateKeyException` 和「先查后插」哪个更可靠？
6. 为什么「加个分布式锁」不等于幂等？

**参考答案要点**
先查后插有竞态窗口：两个相同请求同时过 `SELECT`（都查到没有），再先后 `INSERT`，都成功——并发下「查无」不保证「插时仍无」。正确做法是把「唯一性」交给数据库：建唯一索引 `uk(user_id, item_id, token)`，重复插入直接抛 `DuplicateKeyException`，应用捕获后返回「已下单」而非报错。这比任何应用层判断都可靠，因为唯一索引的约束在存储引擎层原子生效。

幂等令牌链路：下单页先向 `POST /order/token` 领一个 `token`（写 Redis `SET token userId NX EX 300`）；提交时带 `token`，服务端用 `Lua` 原子「校验并删除」——`if redis.call('get',KEYS[1])==ARGV[1] then redis.call('del',KEYS[1]) return 1 else return 0 end`，删除与校验原子，避免「校验通过但删除前被第二个请求再次校验」的重放。令牌是防重放的第一道，唯一索引是兜底。状态机层面，订单从 `CREATED→PAID` 的流转也要幂等：用 `CAS` 或版本号，让重复支付回调只生效一次。

为什么分布式锁 ≠ 幂等：锁只保证同一时刻只有一个请求进入，但锁释放后、或不同 `token`、或重试落在不同节点，锁都不防；幂等要的是「相同输入重复执行结果一致」，靠的是唯一约束和状态机，不是互斥。

```java
if (redisTemplate.execute(tokenScript,
        List.of(tokenKey), userId) == 1L) {
    createOrder(userId, itemId, token); // 校验删除原子，重放被挡
}
```

**可接受的关键结论**
- 先查后插有并发竞态窗口，不能保证幂等；唯一索引 `uk(user_id,item_id,token)` 才是兜底。
- 幂等令牌的校验与删除必须原子（`Lua`），否则有重放窗口。
- 捕获 `DuplicateKeyException` 比「先查后插」可靠，因为约束在引擎层原子生效。
- 分布式锁防并发不防重复，幂等靠唯一约束 + 状态机 CAS，不是靠锁。

**考察意图**
验证候选人是否分得清「互斥」和「幂等」。分水岭在：能否说清先查后插的窗口、用唯一索引兜底、并且点破「加锁 ≠ 幂等」——很多候选人把锁当万能膏药，这一题专门拆它。

**常见错误回答**
- ❌ 「下单前先查有没有这个订单，没有再插」—— 并发下两请求同时查到「没有」，都插成功，锁不住。
- ❌ 「加分布式锁就幂等了」—— 锁只互斥同时刻，重试/换节点/不同 token 都不防。
- ❌ 「令牌校验后单独 `DEL` 删除」—— 校验与删除非原子，中间可被重放再来一次。
- ❌ 「重复下单就让用户自己取消」—— 没兜底，5 亿行里照样产生脏单和资损。
- ❌ 「捕获异常后重试一次」—— 没区分异常类型，重试正好又插一条，越重试越多。

#### 13.5 【关单】订单 15 分钟未支付自动关闭并回滚库存
> **难度**：L2 进阶 ｜ **考察频次**：中 ｜ **目标能力**：方案选型 ｜ **标签**：关单、延迟消息、状态机

**业务场景与约束**
- **业务背景**：下单预占库存后，用户迟迟不付，需要到点自动关单把库存和券放回去。
- **量化约束**：日均 50 万订单；峰值 2000 单/分钟待关闭；关单需回滚库存与优惠券。

**渐进式追问**
1. 用 RocketMQ 延迟消息、Redis ZSet 轮询、定时扫表、Kafka 时间轮，分别怎么实现？
2. 这几种方案在精度、可靠性、实现成本上怎么取舍？
3. 关单和支付回调同时到，怎么保证不出现「关了又付」或「付了又关」？
4. 定时扫表用深分页会慢 SQL，怎么避免？
5. 关单本身失败了怎么补偿重试？

**参考答案要点**
四种实现对比：

| 方案 | 精度 | 可靠性 | 成本 | 适用 |
|------|------|--------|------|------|
| RocketMQ 延迟消息（18 级等级） | 分钟级（等级跳变） | 高，消息不丢 | 低，开箱即用 | 有 RocketMQ 首选 |
| Redis ZSet 轮询 | 秒级 | 中，依赖 Redis 持久化 | 中 | 精度要求高 |
| 定时扫表分页 + 索引 | 取决于扫描间隔 | 高 | 中，需防慢 SQL | 无 MQ 时的兜底 |
| Kafka 时间轮 + 中转 topic | 秒级 | 高 | 高，Kafka 无原生延迟 | 已用 Kafka 且要精度 |

核心是「关单与支付回调的竞态」必须靠状态机，不能先查状态再更新：支付回调到达时 `UPDATE order SET status='PAID' WHERE id=? AND status='CREATED'`（CAS）；关单任务同样 `WHERE status='CREATED'`，两者谁先到谁把状态改成终态，后者 CAS 影响行数为 0 即视为已处理。绝不能用「先 `SELECT status` 判断再 `UPDATE`」——那是竞态重灾区。

扫表避免深分页：`WHERE status='CREATED' AND close_time<now() AND id>? ORDER BY id LIMIT 500` 用「上一页最大 id」游标翻页，走 `(status, close_time, id)` 联合索引，避免 `LIMIT 100000,500` 的回表爆炸。关单失败靠任务幂等重试：CAS 失败即跳过，成功则发回滚消息，回滚库存/券也各自幂等。Kafka 无原生延迟消息，用时间轮把到期消息投到中转 topic 再消费，或外接延迟组件。

**可接受的关键结论**
- 有 RocketMQ 优先用延迟消息，Kafka 场景用时间轮 + 中转 topic 模拟延迟。
- 关单与支付回调的竞态必须用状态机 CAS（`WHERE status='CREATED'`），先查后改必翻车。
- 定时扫表用「上一页最大 id」游标分页 + 联合索引，杜绝深分页慢 SQL。
- 关单与回滚都要幂等，CAS 影响行数为 0 即视为已处理，失败重试安全。

**考察意图**
验证候选人在「延时触发」这道题上会不会选型而不是背名词。分水岭在：能否给出四方案对比表，并明确指出「关单和支付回调的竞态只能靠状态机 CAS，先查后改是坑」——这一句区分了做过和没做过。

**常见错误回答**
- ❌ 「关单前先查订单状态，是 CREATED 就关」—— 查与改之间有窗口，支付回调同时到就会「关了又付」。
- ❌ 「用 `LIMIT 100000,500` 扫表，简单」—— 深分页回表爆炸，越扫越慢，必须游标分页。
- ❌ 「Kafka 也有延迟消息，直接用」—— Kafka 无原生延迟消息（4.0 仅 KRaft），要时间轮或外接组件。
- ❌ 「关单失败不管，下次再扫」—— 没说幂等，回滚库存/券重复执行会多放。
- ❌ 「关单任务用分布式锁保证只跑一次」—— 锁防并发不防「跑一半挂了」，CAS 幂等才靠谱。

#### 13.6 【线程模型】秒杀下单服务线程池怎么配？虚拟线程能直接上吗？
> **难度**：L3 深入 ｜ **考察频次**：中 ｜ **目标能力**：容量估算 ｜ **标签**：线程池、虚拟线程、容量估算

**业务场景与约束**
- **业务背景**：秒杀下单服务是 IO 密集型，但代码里混了少量 CPU 密集逻辑（加解密/风控计算）。
- **量化约束**：容器 8C16G；下游平均 RT 50ms；下单峰值 8000 QPS；JDK 21/25（Java 25 为 2025-09 LTS，Java 21 存量主流）。

**渐进式追问**
1. IO 密集场景下，核心线程数大概按什么公式估算？
2. 队列为什么不能用无界队列？拒绝策略怎么选？
3. 为什么不应直接 `Executors.newFixedThreadPool`？
4. Tomcat 线程池和业务线程池为什么要隔离？
5. 虚拟线程（Java 21 转正，JEP 444）适不适合这里？什么情况反而不适合？
6. synchronized pinning 在 JDK 24（JEP 491）才解决，对上虚拟线程意味着什么？

**参考答案要点**
IO 密集容量估算：核心线程数 ≈ 期望并发 = QPS × 平均 RT = 8000 × 0.05s = 400 个并发任务。若下游 RT 50ms 且大部分时间在等网络，平台线程池配核心 400、最大 400~600，`keepAlive` 短一点即可。队列绝不能用无界：`LinkedBlockingQueue` 无界会在下游抖动时无限堆积，把内存和 P99 拖爆；应使用有界队列（如 200~500）配 `CallerRunsPolicy`——满了让调用方自己跑，既限流又保护下游。

为什么不用 `Executors.newFixedThreadPool`：它默认无界队列 + 固定线程，下游一抖就堆积到 OOM，且线程数写死不灵活。`Tomcat` 线程池（处理 HTTP）和业务线程池（跑下单逻辑）要隔离：否则一个慢下游把 Tomcat 线程占满，连带健康接口也 503，故障扩散。

虚拟线程：Java 21 转正（JEP 444），适合「大量阻塞 IO、少量计算」——它用少量载体线程承载海量虚拟线程，吞吐量高、写起来像同步代码。但不直接无脑上：① 若真瓶颈是连接池（DB/Redis 连接数固定），虚拟线程再多也挤在等连接，吞吐不增；② CPU 密集逻辑混在里面会长期占住载体线程，抵消优势；③ `synchronized` 在虚拟线程上会 pinning（把载体线程钉死），直到 JDK 24（JEP 491）才解决，JDK 21/25 上要改用 `ReentrantLock`。引入姿势：先把同步阻塞调用迁到虚拟线程 + 用 `ReentrantLock` 替代 `synchronized`，并确认下游是 IO 而非连接池瓶颈，再灰度。

**可接受的关键结论**
- IO 密集核心线程数 ≈ QPS × 平均 RT（本题约 400），队列必须有界，拒绝策略用 `CallerRunsPolicy` 限流。
- 别用 `newFixedThreadPool`：无界队列 + 抖动 = OOM；Tomcat 与业务线程池必须隔离防故障扩散。
- 虚拟线程适合阻塞 IO 多的场景，但连接池才是真瓶颈时上了也没用。
- 虚拟线程 + `synchronized` 在 JDK 21/25 会 pinning，JEP 491（JDK 24）才解决，要改用 `ReentrantLock`。

**考察意图**
验证候选人会不会「按容量算线程数」而不是拍脑袋。分水岭在：能否给出 8000×0.05≈400 的估算、点破无界队列的 OOM 风险，并说清虚拟线程的适用边界与 pinning 这个具体坑——背过名词的人说不出 JEP 491。

**常见错误回答**
- ❌ 「线程数设成 CPU 核数 × 2 就行」—— 那是 CPU 密集公式，IO 密集要按 QPS×RT 估算，本题约 400。
- ❌ 「用 `newFixedThreadPool` 省事」—— 无界队列，下游抖一下就堆积到 OOM。
- ❌ 「队列设大一点更稳」—— 无界/超大队列把 RT 和内存拖爆，限流能力归零。
- ❌ 「上虚拟线程就完事，不用管线程池」—— 连接池瓶颈 + CPU 密集混算下，虚拟线程毫无收益甚至更差。
- ❌ 「虚拟线程里随便用 `synchronized`」—— JDK 21/25 会 pinning 钉死载体线程，得换 `ReentrantLock`（JEP 491 才解）。
- ❌ 「Tomcat 和业务共用一个线程池简单」—— 慢下游占满 Tomcat 线程，健康接口也跟着 503。

#### 13.7 【RT 抖动】下单接口 P99 从 50ms 涨到 800ms，但 CPU 和 DB 都正常
> **难度**：L3 深入 ｜ **考察频次**：中 ｜ **目标能力**：排障思路 ｜ **标签**：RT 抖动、长尾、链路追踪

**业务场景与约束**
- **业务背景**：下单接口白天偶发长尾超时，但监控上 CPU、DB 都「正常」，均值也正常。
- **量化约束**：仅 10% 采样日志 + 监控面板；平均 RT 仍 55ms；超时率 0.3%；集中在 20:00–22:00 高峰。

**渐进式追问**
1. 平均值 55ms 但 P99 800ms，这本身说明了什么？
2. 怎么用链路追踪定位到具体慢在哪一段（span）？
3. GC 停顿会不会是元凶？该怎么查而不是瞎猜？
4. 线程池队列在等，为什么看 CPU 是「正常」的？
5. `CompletableFuture` 默认共用 `ForkJoinPool` 会带来什么坑？
6. 为什么「CPU 正常」就排除 JVM 问题是错的？

**参考答案要点**
均值正常、P99 暴涨 = 长尾：少数请求极慢把分位拉高，但被大量快请求平均掉了，所以看均值会误判。第一步用链路追踪按 P99 采样（而非全量或按均值），把慢请求的具体 span 拉出来——是「调用下游」「查 DB」还是「线程等待」，一眼定位，而不是盯大盘。

常见真凶按优先级：① 线程池队列等待——请求在队列里排长队，线程本身空闲、CPU 当然「正常」，必须看队列长度而非 CPU；② GC 停顿——用 `-Xlog:gc*`（JDK 9+ 语法，别再用 `-XX:+PrintGCDetails`）看 `Pause` 时长，长尾往往对应一次上百毫秒的 Full GC/大对象分配；③ 连接池等待——HikariCP/Druid 连接借不到在等，监控只显示「DB 正常」；④ `CompletableFuture` 默认跑在公共 `ForkJoinPool.commonPool()`，一旦某处慢任务占满，所有用默认池的异步逻辑互相拖累，长尾被放大——应自定义线程池；⑤ 下游 50ms 抖动在串行调用里被乘成 800ms。

为什么「CPU 正常就排除 JVM」错：卡在锁、队列、GC 安全点、连接等待时，线程是 blocked/waiting，不消耗 CPU，CPU 自然低；JVM 的停顿类问题恰恰表现为「CPU 低但 RT 高」。排障要按 trace 而非按 CPU。

**可接受的关键结论**
- 均值正常 P99 高 = 长尾，被大量快请求平均掩盖，必须按 P99 采样看 trace 而非盯均值。
- 卡在队列/锁/GC/连接等待时线程是 waiting，CPU 反而低，「CPU 正常」不能排除 JVM 问题。
- GC 用 `-Xlog:gc*` 看停顿，线程池要看队列长度，连接池要看等待次数。
- `CompletableFuture` 别用默认 `ForkJoinPool`，自定义线程池避免互相拖累。

**考察意图**
验证候选人有没有「系统性排障」的肌肉记忆。分水岭在：能否从「均值正常但 P99 高」推出长尾、并指出「CPU 正常恰恰说明线程在等」这个反直觉点，而不是无脑说「加机器/优化 SQL」。

**常见错误回答**
- ❌ 「平均才 55ms 说明没问题，不用管」—— P99 800ms 是真实长尾超时，被均值掩盖了。
- ❌ 「用 `-XX:+PrintGCDetails` 看 GC」—— JDK 9+ 已废弃，应统一用 `-Xlog:gc*`。
- ❌ 「CPU 不高就说明不是 JVM 的问题」—— 等锁/等队列/GC 安全点时线程 waiting，CPU 本就低。
- ❌ 「线程池配大点就好了」—— 没先看队列长度，盲目加线程只会加剧上下文切换和下游压力。
- ❌ 「直接 `jstack` 看哪个线程忙」—— 长尾时线程多在等，该看 trace 的慢 span 和队列/池等待，不是看谁忙。
- ❌ 「`CompletableFuture` 用默认池方便」—— 公共池被一处慢任务占满，所有异步逻辑被拖成长尾。

#### 13.8 【防刷限流】黄牛脚本 5 万 QPS 打下单接口
> **难度**：L2 进阶 ｜ **考察频次**：高 ｜ **目标能力**：分层防御 ｜ **标签**：限流、防刷、熔断降级

**业务场景与约束**
- **业务背景**：黄牛用脚本刷下单接口抢货转卖，真实用户被挤在门外。
- **量化约束**：正常用户峰值 8000 QPS；黄牛脚本峰值 5 万 QPS；单机 500 QPS 承载能力；要尽力放行真实用户。

**渐进式追问**
1. 只在一个地方限流够吗？应该分哪几层？
2. 令牌桶、漏桶、滑动窗口分别适合哪一层？
3. 用 Redis + Lua 做集群限流，单机限流在集群下会放大多少？
4. 限流之外的风控还能做什么？
5. 下游快扛不住时，熔断和降级怎么配合快速失败？

**参考答案要点**
单一限流必漏，要分层：① 网关层按「总 QPS / 单 IP / 单用户」限流，把 5 万 QPS 在入口砍到接近 8000；② 接口维度限流，保护下单自身；③ 库存维度限流，库存剩多少就放多少请求进扣减；④ 业务维度用令牌桶做「匀速放行」，平滑突发。

算法选型：网关入口用令牌桶（允许短时突发、平滑），需刚性限速用漏桶（恒定速率、削峰），需要更准的瞬时计数用滑动窗口（比固定窗口少一倍临界突刺）。集群限流用 Redis + Lua 原子计数（`INCR+EXPIRE` 或 `ZSet` 时间窗），但单机限流在 N 台机器下总配额被放大 N 倍——若单机限 500，10 台集群实际放 5000，必须改成「中心化 Redis 计数 / 或单机配额 = 总配额/N」并留余量。

限流只是第一道，黄牛会换 IP/账号绕过，必须叠风控：设备指纹（同设备多账号）、行为验证（答题/滑块）、历史黑名单、下单频次异常检测。下游抖动时熔断（如基于错误率/RT 的熔断器）打开，降级为「排队中/稍后重试」快速失败，避免线程被黄牛打满拖垮真实用户。预热冷启动：活动开始瞬间逐步放开配额，防瞬时击穿。

**可接受的关键结论**
- 限流要分层：网关 QPS → 用户 → 接口 → 库存，单层必漏。
- 集群下单机限流总配额被放大 N 倍，必须中心化 Redis 计数或配额按 N 均分。
- 令牌桶/漏桶/滑动窗口按「要突发/要刚性/要精准」选层，不是万能一个。
- 限流挡不住换 IP 黄牛，必须叠设备指纹/行为验证/黑名单；下游快崩时用熔断降级快速失败。

**考察意图**
验证候选人会不会「立体防御」而不是堆一个限流中间件。分水岭在：能否指出集群下单机限流的 N 倍放大误差、并自然带出风控与熔断降级——只会配一个 `sentinel` 规则的人答不到这层。

**常见错误回答**
- ❌ 「在接口里加个限流注解就行」—— 单层限流，黄牛换 IP/账号就绕过，真实用户仍被挤。
- ❌ 「每台机器限 500 QPS 就够了」—— 10 台集群实际放 5000，总配额被放大 N 倍，必须中心化。
- ❌ 「限流配大点别误杀真实用户」—— 不分层不风控，大配额直接被黄牛 5 万吃满。
- ❌ 「限流用漏桶最准」—— 漏桶削峰但无突发，入口用令牌桶更贴合「放行真实突发」的诉求。
- ❌ 「黄牛靠限流就防住了」—— 没设备指纹/行为验证，黄牛换 IP 秒破。
- ❌ 「下游慢就加机器」—— 不熔断降级，黄牛把线程打满，加机器也被冲垮。
