#### 16.1 【接口超时】用户反馈下单偶发超时，上游 3s 超时、下游 RT 显示正常，怎么定位？
> **难度**：L3 深入 ｜ **考察频次**：高 ｜ **目标能力**：故障定位 ｜ **标签**：链路追踪、超时、连接池

**业务场景与约束**
- **业务现象**：用户侧偶发下单超时，上游网关 3s 硬超时触发；下游服务监控面板"RT 一切正常"；客服工单集中在晚高峰。
- **量化约束**：超时率 0.3%；只发生在 20:00–22:00；日均 50 万单；服务端平均 RT 仍显示 55ms；下游监控显示 P99 仅 60ms、错误率 0。

**渐进式追问**
1. 超时率只有 0.3% 且据说是"偶发"，你会先用什么指标确认它发生在客户端、网关、服务端还是下游，而不是先怀疑代码？
2. 平均 RT 55ms 但用户感知超时，这说明耗时分布上有什么特征？你会盯 P99 还是均值？
3. 下游监控"一切正常"为什么可能是监控口径在骗你？你怎样用链路追踪拿到真实的分段耗时？
4. 如果定位到服务端但 CPU 不高，你会优先看线程池队列还是数据库连接池？怎么量化它们的等待？
5. 日志里为什么必须带 `traceId` 且按"网关→服务→下游→DB"分段记耗时，而非只记总耗时？
6. 晚高峰 20–22 点才出现，GC 停顿和连接池争用哪个更可能？你怎么用 `jstat` 和 HikariCP 指标排除？
7. 根治之后，你靠什么监控防止它复发——错误采样率还是全量埋点？

**参考答案要点**
- **定位路径**：先界定故障发生在哪一段 → 用 P99 而非均值确认长尾 → 用分段耗时工具证实 → 量化等待资源 → 根治并加监控。顺序不能乱，先界定再深挖，否则容易在错误组件上花时间。
- **界定范围**：用网关访问日志（带 `traceId`）对比服务端收到请求的时间戳，若差距大就是网络 / DNS / 网关层；若服务端收得到但处理慢，才进服务端排查。
- **看长尾**：平均 55ms 但用户超时，说明是 P99 长尾而非均值问题。监控必须按 `P99` 或错误采样，全量均值会把尖刺抹平——这正是 0.3% 超时查不到的根因。
- **分段耗时**：下游"RT 正常"常是口径骗局——下游只统计已到达它的请求，网关到下游的排队、建连、 DNS 它看不到。链路追踪（`traceId` 贯穿全链路）才能拿到"网关→服务→下游→DB"各段真实耗时。
- **量化等待**：CPU 不高时优先看线程池队列长度（等待线程数）和连接池 pending（`HikariCP` 的 `connectionTimeout`、`activeCount`，Druid 的 `waiting`）。GC 停顿看 `jstat -gcutil` 的 `YGCT`/`FGCT`。
- **根因假设**：晚高峰连接池争用或 `TIME_WAIT` 堆积，用 `netstat -an | grep TIME_WAIT | wc -l` 验证。

```bash
jstat -gcutil <pid> 1s          # 看 GC 次数与停顿累计
netstat -an | grep TIME_WAIT | wc -l   # 验证 TIME_WAIT 堆积
```

**可接受的关键结论**
- 平均 RT 正常但超时，必须按 P99 或错误采样排查，均值会掩盖长尾。
- "下游 RT 正常"常是口径骗局，下游只统计已到达请求，排队与建连它看不到，必须靠 `traceId` 分段耗时。
- 服务端 CPU 不高时优先排查线程池队列与数据库连接池 pending，而非盲猜代码慢。
- 日志必须带 `traceId` 且分段记耗时，否则无法定位慢在哪一跳。
- 复发防护靠错误采样告警 + 连接池 / 队列长度监控，而非全量埋点。

**考察意图**
验证"从现象倒推"的系统化定位能力。L2 与 L3 的分水岭在"下游 RT 正常"那一句：能指出监控口径会骗人、坚持用分段耗时和 P99 证实的是 L3；只说"看日志找慢在哪里"的是 L2。前者展现对监控盲区和方法论的意识，后者停留在操作层面。

**常见错误回答**
- ❌ "先重启试试，不行再加机器" —— 错在把现场证据洗掉且没定位就扩容；正确是先界定故障段再量化。
- ❌ "平均 RT 才 55ms 说明没问题" —— 错在用均值掩盖 P99 长尾；正确盯 P99 / 错误采样。
- ❌ "下游说正常就是下游没问题" —— 错在信监控口径；下游只统计已到达请求，排队建连它看不到。
- ❌ "加个 Redis 缓存就好了" —— 错在没定位就上方案；超时未必是 DB 慢，可能是连接池争用。
- ❌ "日志打总耗时就够了" —— 错在无法分段定位；必须 `traceId` 分段记各跳耗时。

#### 16.2 【CPU 飙高】Java 进程 CPU 900%，5 分钟内定位到代码行
> **难度**：L2 扎实 ｜ **考察频次**：高 ｜ **目标能力**：工具链熟练度 ｜ **标签**：CPU、线程栈、jstack、Arthas

**业务场景与约束**
- **业务现象**：Java 进程 CPU 冲到 900%，接口大量超时，业务告警；运维想重启但被叫停。
- **量化约束**：容器 8C；CPU 900%（约等于吃满 7.2 核）；要求 5 分钟内定位到具体代码行；**不能重启、要保留现场**；GC 日志无异常、无 Full GC。

**渐进式追问**
1. 不能重启且要保现场，你第一步会动哪个工具，为什么不能先重启？
2. `top` 只能看到进程级 CPU，怎么下钻到具体线程？
3. `jstack` 看到的线程 `nid` 是 16 进制，怎么把 `top` 里的 tid 对应上？
4. 为什么 `jstack` 抓一次就下结论是不可靠的，要看什么？
5. 除了 `jstack`，Arthas 和 async-profiler 各自适合什么场景？
6. GC 日志无异常，你能排除哪些 CPU 飙高的成因？

**参考答案要点**
- **保现场优先**：容器 8C 但 CPU 900% 且不能重启，第一步是保留证据——先做线程 dump 和（必要时）heap dump，再考虑恢复。重启即销毁现场，复盘只能靠猜。
- **线程级下钻**：`top -Hp <pid>` 找出 CPU 最高的线程 tid，用 `printf '%x\n' <tid>` 转 16 进制得到 `nid`，再 `jstack <pid> | grep -A 20 "nid=0x..."` 定位栈帧。注意 `top` 只到进程，必须 `-H` 到线程。
- **多次采样**：单次 `jstack` 可能抓到处于安全点的线程造成误判，要在 1–2 秒内连抓 2–3 次，取交集确认同一方法持续占 CPU。
- **替代与增强**：`jcmd <pid> Thread.print` 是 JDK 9+ 推荐的等价命令；Arthas `thread -n 3` 直接列出最忙 3 个线程，免手动转 nid；async-profiler 出火焰图，适合找"热点方法"而非单点死循环。
- **常见成因**：死循环、正则灾难性回溯、`Thread.sleep`/锁竞争导致的大量上下文切换、频繁 GC（本例 GC 日志正常可排除）、序列化热点。
- **根因确认**：多次采样都指向同一方法 + 火焰图热点吻合，即可定位；必要时 `jcmd <pid> GC.heap_dump`（注意会 STW）留存。

```bash
top -Hp <pid>                       # 找高 CPU 线程 tid
printf '%x\n' <tid>                 # tid 转 16 进制 nid
jstack <pid> | grep -A 20 "nid=0x..."  # 定位栈帧
```

**可接受的关键结论**
- 先 thread dump / heap dump 保现场，再考虑重启——重启即销毁证据。
- `top -Hp` 下钻到线程，`printf` 转 16 进制后 `jstack` 搜 `nid` 定位栈。
- 单次 `jstack` 不可靠，要多次采样取交集，避免安全点误判。
- GC 日志正常时应优先排查死循环、正则回溯、上下文切换，而非盲调堆。
- Arthas `thread -n 3` 和 async-profiler 火焰图能更快锁定热点方法。

**考察意图**
验证工具链熟练度与"保现场"意识。L2 分水岭在会不会先用 `top -Hp` → `jstack` 这条标准链路，并知道多次采样；L3 还会补一句"先 dump 再重启、用火焰图确认热点"。只说"用 `top` 看一眼"或"重启试试"的，说明没有现场意识。

**常见错误回答**
- ❌ "直接 `jstack` 一次就定位了" —— 一次可能抓到安全点假象；正确多次采样取交集。
- ❌ "CPU 高先重启" —— 重启销毁现场无法复盘；正确先 dump 再恢复。
- ❌ "肯定是 GC，调 `-Xmx`" —— GC 日志已无异常还盲调堆；正确先定位线程栈热点。
- ❌ "用 `top` 看进程就够" —— `top` 只到进程看不到线程；要 `top -Hp` 到线程再转 nid。
- ❌ "加机器扩核" —— 死循环扩核只会更卡；先找到热点方法再说。

#### 16.3 【Full GC】每隔 10 分钟 Full GC 一次，每次 STW 800ms
> **难度**：L3 深入 ｜ **考察频次**：中 ｜ **目标能力**：内存分析 ｜ **标签**：Full GC、G1、MAT、堆外

**业务场景与约束**
- **业务现象**：服务每隔约 10 分钟一次 Full GC，接口 P99 出现周期性尖刺；老年代占用呈锯齿状。
- **量化约束**：堆 4G、G1 收集器、JDK 21；每次 Full GC STW 约 800ms；老年代占用升到 80% 后被回收；接口 P99 周期性从 50ms 跳到 800ms+。

**渐进式追问**
1. 你会先用哪条命令确认 Full GC 的频率和停顿，而不是凭感觉调参？
2. 怎么判断这是"内存泄漏"还是"容量不足"？看哪个指标？
3. 要做堆分析，为什么用 `jcmd` 而不是已废弃的旧命令？
4. MAT 里应该看 shallow size 还是 dominator tree，为什么？
5. G1 下有哪些参数和对象类型会加剧 Full GC，比如 Humongous？
6. 你定位到泄漏源后，根治和临时止血分别怎么做？

**参考答案要点**
- **先确认再调参**：用 `-Xlog:gc*:file=gc.log:time,uptime,level,tags` 和 `jstat -gcutil <pid> 1s` 拿到 Full GC 频率与停顿，而不是凭"感觉慢"就加堆。
- **泄漏 vs 容量**：关键看每次回收后老年代基线——锯齿但能回到底部是容量不足（对象该回收的都回收了），只升不回、基线持续抬升是内存泄漏。这是 L2/L3 的分水岭。
- **堆快照**：`jcmd <pid> GC.heap_dump /tmp/heap.hprof`（注意会 STW，选低峰）。不要用已废弃的 jmap 堆统计子命令。MAT 看 **dominator tree（支配树）** 找支配者，而非 shallow size——支配者才是"掐住它就能释放一大片"的真凶。
- **常见泄漏源**：ThreadLocal 未 `remove`、静态集合持续 add、未关闭的连接 / 流、堆外内存、类加载器泄漏（热部署常见）。
- **G1 要点**：`MaxGCPauseMillis` 设目标、`InitiatingHeapOccupancyPercent`（IHOP）控制并发标记触发点；**Humongous 对象**（超过 region 50%）会绕过年轻代直接进入老年代并触发混合回收混乱，是大对象分配的雷区。JDK 25 起 G1 全环境默认分代。
- **根治**：泄漏就修掉未释放的引用；容量不足就扩堆或调高 IHOP，让并发标记提前。

```bash
-Xlog:gc*:file=gc.log:time,uptime,level,tags
jstat -gcutil <pid> 1s
jcmd <pid> GC.heap_dump /tmp/heap.hprof
```

**可接受的关键结论**
- 先用 `-Xlog:gc*` 和 `jstat -gcutil` 确认，严禁用 JDK 8 时代已废弃的 GC 打印参数。
- 区分泄漏与容量看老年代回收后基线：只升不回是泄漏，锯齿回底是容量不足。
- 堆分析用 `jcmd GC.heap_dump` + MAT 支配树，不看 shallow size。
- G1 要关注 Humongous 对象（> region 50%）和 IHOP 设置。
- 容量不足扩堆或调 IHOP，泄漏必须修掉未释放引用，加堆只是延后爆发。

**考察意图**
验证内存问题归因能力。L2 与 L3 的分水岭在能否区分"泄漏"与"容量不足"：只看 GC 频繁就加堆的是 L2，看老年代基线抬升判断泄漏、并用支配树定位真凶的是 L3。后者展现对内存生命周期的理解，前者停留在"加内存"的本能反应。

**常见错误回答**
- ❌ "Full GC 频繁就加堆到 8G" —— 若是泄漏，加堆只是延后爆发；先判断泄漏 vs 容量。
- ❌ "用已废弃的 GC 详情打印参数看日志" —— 该写法 JDK 9+ 已废弃；用 `-Xlog:gc*`。
- ❌ "用已废弃的 jmap 堆统计子命令看堆" —— 该命令过时且有风险；用 `jcmd GC.heap_dump` + MAT。
- ❌ "老年代 80% 就回收是正常的" —— 锯齿回升到 80% 且接口周期尖刺，要查 Humongous 或 IHOP。
- ❌ "MAT 看最大的是谁就行" —— 要看 dominator tree 支配者，shallow size 会误导。

#### 16.4 【线程池打满】队列积压、拒绝策略疯狂触发
> **难度**：L1 基础 ｜ **考察频次**：高 ｜ **目标能力**：容量与隔离 ｜ **标签**：线程池、拒绝策略、隔离、熔断

**业务场景与约束**
- **业务现象**：高峰时段线程池队列持续积压，拒绝策略每分钟触发上万次，部分请求直接被拒。
- **量化约束**：核心线程 20、最大 50、队列 2000；峰值流量是平时 3 倍；拒绝次数每分钟上万；下游依赖响应正常。

**渐进式追问**
1. 队列在涨、任务也在完成，你怎么判断是"任务变多"还是"下游变慢"？
2. 为什么无界队列在大流量下是定时炸弹，和本例的有界队列有什么区别？
3. 四种拒绝策略分别适合什么场景，CallerRunsPolicy 为什么可能反噬上游？
4. 一个线程池跑所有业务接口会有什么问题，怎么改？
5. 队列长度和拒绝次数要不要监控，监控不到会怎样？
6. 虚拟线程能不能直接解决这次的问题？

**参考答案要点**
- **先分根因**：看队列增长速率 vs 单任务耗时。若耗时不变、队列只涨，是任务变多（下游没慢）；若耗时涨、队列同步涨，是下游变慢拖住线程。本例下游正常，说明是流量 3 倍导致的任务量暴涨。
- **无界队列是雷**：用 `LinkedBlockingQueue` 不指定容量等于 `Integer.MAX_VALUE`，任务无限堆积最终 OOM。本例用有界队列 2000，所以表现为拒绝而非 OOM——有界反而更"诚实"地暴露问题。
- **拒绝策略取舍**：`AbortPolicy`（默认，抛异常）、`CallerRunsPolicy`（让调用方线程自己跑被拒任务）、`DiscardPolicy`（静默丢）、`DiscardOldestPolicy`（丢最老）。`CallerRunsPolicy` 看似友好，但若调用方是 Tomcat 业务线程，会把它也占满，反而拖垮整个 HTTP 入口——这是典型的反噬。
- **隔离**：不同业务必须用不同线程池，否则一个慢接口占满线程会拖垮全部接口。
- **监控与兜底**：队列长度、活跃线程数、拒绝次数必须上报告警；配合动态调参、降级与熔断。
- **虚拟线程边界**：虚拟线程能解"线程数不够"，但解不了"下游能力不足"——下游慢，换虚拟线程照样阻塞。

**可接受的关键结论**
- 先用队列增长速率 vs 单任务耗时区分"任务变多"还是"下游变慢"。
- 无界队列是 OOM 定时炸弹，必须显式容量；有界队列拒绝是更诚实的暴露。
- `CallerRunsPolicy` 可能用调用方线程跑任务，反噬 Tomcat 入口，需评估后使用。
- 不同业务必须隔离线程池，避免一个慢接口拖垮全部。
- 虚拟线程解线程数瓶颈，解不了下游能力不足；队列与拒绝次数必须监控。

**考察意图**
验证容量与隔离的基本功，这是本模块的 L1 锚点，应届生也应答出。分水岭在知不知道无界队列是 OOM 定时炸弹、`CallerRunsPolicy` 会反噬上游——能讲清这两点的说明真正用过线程池而非背过定义；只说"用线程池提高性能"的，说明停留在概念层。

**常见错误回答**
- ❌ "队列设成无界 `Integer.MAX_VALUE` 不就好了" —— 无界队列是 OOM 定时炸弹；必须显式容量。
- ❌ "拒绝策略用 CallerRuns 最安全" —— 它会用调用方线程跑任务，若调用方是 Tomcat 线程会拖垮 HTTP；要评估。
- ❌ "一个线程池跑所有任务" —— 慢接口会拖垮全部；必须按业务隔离。
- ❌ "拒绝就丢，用户重试" —— 丢弃 + 重试放大可能雪崩；要降级 + 熔断。
- ❌ "虚拟线程能解决一切" —— 虚拟线程解线程数不够，解不了下游能力不足。

#### 16.5 【慢 SQL】订单列表查询从 20ms 涨到 3s
> **难度**：L2 扎实 ｜ **考察频次**：高 ｜ **目标能力**：索引与执行计划 ｜ **标签**：慢SQL、执行计划、联合索引、分页

**业务场景与约束**
- **业务现象**：订单列表查询在大用户身上延迟从 20ms 飙到 3s，小用户正常。
- **量化约束**：单表 2 亿行；SQL 为 `WHERE user_id = ? AND status = ? ORDER BY create_time DESC LIMIT 20`；只在部分用户身上复现；慢日志阈值 1s 已开启采样。

**渐进式追问**
1. 你会先跑什么命令看这条 SQL 的执行计划，重点看哪几列？
2. 现有查询要快，联合索引应该怎么建，顺序有什么讲究？
3. `ORDER BY create_time` 会不会导致 filesort，怎么消掉？
4. 深分页 `LIMIT 100000, 20` 有什么代价，游标分页怎么写？
5. 哪些常见写法会让索引失效，比如函数、隐式转换、前导模糊？
6. 为什么只在部分用户复现，是索引问题还是数据问题？

**参考答案要点**
- **看执行计划**：`EXPLAIN` 重点看 `type`（要到 `ref`/`range` 才算用到索引）、`key`（实际走的索引）、`rows`（扫描行数）、`Extra`（警惕 `Using filesort` 和 `Using temporary`）。`Extra` 里的 filesort 往往比 `rows` 更致命。
- **联合索引**：建 `(user_id, status, create_time)` 满足最左前缀，`WHERE` 两列等值 + `ORDER BY create_time` 可被索引消除排序。若把 `status` 放 `create_time` 之后，排序字段断掉，`ORDER BY` 就退化成 filesort。
- **覆盖索引**：`SELECT` 只取索引列（或包含列）可避免回表，进一步降延迟。
- **深分页代价**：`LIMIT 100000, 20` 要先扫 10 万行再丢弃，越翻越慢。改写游标分页 `WHERE create_time < ? ORDER BY create_time DESC LIMIT 20`，或延迟关联先查 ID 再 `JOIN`。
- **失效写法**：函数包裹列（`DATE(col)`）、隐式类型转换（`user_id` 是字符串却传数字）、`OR` 拼接、`LIKE '%x'` 前导模糊、不等号 `!=` 都可能让索引失效。
- **部分用户复现**：数据倾斜（大用户订单几百万行）+ 优化器选错索引，导致小用户走索引、大用户走全表。`ANALYZE TABLE` 更新统计或临时 `FORCE INDEX` 救急，根治是改索引设计。

```bash
EXPLAIN SELECT * FROM orders
  WHERE user_id=? AND status=?
  ORDER BY create_time DESC LIMIT 20;
```

**可接受的关键结论**
- 用 `EXPLAIN` 看 `type`/`key`/`rows`/`Extra`，`Using filesort` 比 `rows` 更值得警惕。
- 联合索引 `(user_id, status, create_time)` 满足最左前缀并消除排序，顺序不能乱。
- 深分页 `LIMIT 100000,20` 代价大，用游标分页或延迟关联改写。
- 函数 / 隐式转换 / 前导模糊 / `OR` 会让索引失效，保持类型与写法一致。
- 部分用户复现多为数据倾斜 + 优化器选错索引，靠 `ANALYZE TABLE` 或 `FORCE INDEX` 救急。

**考察意图**
验证索引与执行计划的实战能力。L2 分水岭在会不会用 `EXPLAIN` 的 `Extra` 定位 filesort、会不会用覆盖索引和游标分页解决深分页——能讲清联合索引顺序与排序消除关系的，说明真在线上调过慢 SQL；只说"加索引"三个字的，说明没碰过 2 亿行表的执行计划。

**常见错误回答**
- ❌ "加个索引就行" —— 没说联合索引顺序，`ORDER BY` 可能仍 filesort；要 `(user_id, status, create_time)`。
- ❌ "用 `LIKE '%关键词%'` 也能走索引" —— 前导模糊不走索引，全表扫描；改后缀或上 ES。
- ❌ "深分页 `LIMIT 100000,20` 没事" —— 要扫 10 万行再丢；改游标分页。
- ❌ "`user_id` 传数字没事" —— 列是字符串会被隐式转换导致索引失效；保持类型一致。
- ❌ "看 `rows` 小就是快" —— 要看 `type` 和 `Extra`，filesort / temporary 比 `rows` 更致命。

#### 16.6 【OOM】容器半夜被 OOMKilled，但堆监控只用了 60%
> **难度**：L3 深入 ｜ **考察频次**：中 ｜ **目标能力**：内存全局观 ｜ **标签**：OOM、RSS、堆外内存、NMT

**业务场景与约束**
- **业务现象**：容器半夜被 OOMKilled（退出码 137），但 JVM 堆监控峰值只有 1.5G，看似远未到上限。
- **量化约束**：容器 limit 4G；`-Xmx 2.5G`；JVM 堆监控峰值 1.5G；容器 RSS 持续涨到 4G 后被 kill；发生在凌晨批处理时段。

**渐进式追问**
1. 为什么堆只用 60% 还会被 OOMKilled，JVM 占用等于堆占用吗？
2. 堆外内存通常来自哪些地方，怎么确认是堆外漏？
3. 用什么命令看 JVM 各内存区域的真实占用？
4. `-XX:MaxDirectMemorySize` 不设会有什么后果？
5. 容器里 JVM 怎么正确感知 cgroup 限制，避免按宿主机算资源？
6. 给容器留多少余量算工程常识？

**参考答案要点**
- **认知纠偏**：JVM 实际占用 ≠ 堆。容器 RSS = 堆 + 元空间 + 线程栈 + 直接内存 + CodeCache + GC/JIT 开销，**RSS > Xmx 是常态**。本例堆 1.5G 但 RSS 到 4G，说明泄漏在堆外，堆监控当然"正常"。
- **堆外来源**：Netty `DirectByteBuffer`、gRPC、压缩库（如 snappy）、glibc malloc arena 碎片、未释放的 `ByteBuffer`。凌晨批处理时段大量序列化最易触发。
- **量化与诊断**：`-Xmx 2.5G` 给 4G 容器理论留 1.5G 余量，但堆外无上限就会突破。开 `-XX:NativeMemoryTracking=summary` 后用 `jcmd <pid> VM.native_memory summary` 看各区域真实占用。
- **必须显式上限**：`-XX:MaxDirectMemorySize` 不设时默认等于 Xmx，但堆外（如 glibc arena、CodeCache）仍可能涨，必须显式设上限并监控。
- **容器感知**：`-XX:+UseContainerSupport`（JDK 10+ 默认开）让 JVM 读 cgroup；用 `-XX:MaxRAMPercentage=75` 自动按容器 limit 算堆，别写死 `-Xmx` 顶满。
- **工程常识**：给容器留 25–30% 余量，Xmx 别顶满 limit，否则堆外一涨就必死。

```bash
jcmd <pid> VM.native_memory summary   # 需 -XX:NativeMemoryTracking=summary
```

**可接受的关键结论**
- JVM 占用 ≠ 堆，RSS = 堆 + 元空间 + 栈 + 直接内存 + CodeCache + GC/JIT，RSS > Xmx 是常态。
- OOMKilled 但堆低，优先怀疑堆外泄漏（Netty、gRPC、压缩库、arena 碎片）。
- 用 `jcmd VM.native_memory` 看各区域，需开 NMT。
- 必须显式设 `-XX:MaxDirectMemorySize`，否则堆外仍可能涨爆。
- 容器里留 25–30% 余量，用 `MaxRAMPercentage` 而非写死 `-Xmx` 顶满。

**考察意图**
验证内存全局观。L2 与 L3 的分水岭在是否知道 RSS > Xmx 是常态、会不会用 NMT 查堆外、是否显式设 `MaxDirectMemorySize`——知道"堆只占 JVM 一部分"的是 L3，盯着堆监控说"没满不可能 OOM"的是 L2。后者缺的是对进程内存构成的整体认知。

**常见错误回答**
- ❌ "堆才用 60% 不可能 OOM" —— OOM 是容器 RSS 超 limit 被杀，堆外不计入 Xmx；要看 NMT。
- ❌ "不设 `MaxDirectMemorySize`" —— 默认等于 Xmx，但堆外（arena/CodeCache）仍可能涨爆；必须显式设上限。
- ❌ "JVM 占用 = 堆占用" —— RSS 含元空间 / 栈 / 直接内存 / CodeCache；要全局看。
- ❌ "把 `-Xmx` 设到 limit 的 95%" —— 不留余量，堆外一涨就 kill；留 25–30%。
- ❌ "容器里不用 `-XX:+UseContainerSupport`" —— 不感知 cgroup 会按宿主机算核数 / 内存；JDK 10+ 默认开但应确认。

#### 16.7 【数据库死锁】两个账户互相转账偶发死锁
> **难度**：L2 扎实 ｜ **考察频次**：中 ｜ **目标能力**：锁与并发 ｜ **标签**：死锁、InnoDB、加锁顺序、重试

**业务场景与约束**
- **业务现象**：转账业务偶发报错 `Deadlock found when trying to get lock`，需重试才能成功。
- **量化约束**：转账 500 TPS；账户表 8000 万行；MySQL 8.0 / InnoDB / RR 隔离 + row 格式 binlog；每天几十次死锁。

**渐进式追问**
1. 死锁的根本成因是什么，和"锁等待超时"是一回事吗？
2. 你用什么命令看到最近一次死锁的等待图和涉及事务？
3. 根治手段是什么，为什么要固定加锁顺序？
4. 缩小事务范围为什么能降低死锁概率？
5. 降低隔离级别到 RC 有什么利弊，binlog 要配什么格式？
6. 业务层加重试就够了吗，重试要注意什么？

**参考答案要点**
- **根因**：死锁是**加锁顺序不一致**导致的环。A 向 B 转（先锁 A 再锁 B）和 B 向 A 转（先锁 B 再锁 A）并发时，各自持有一把等另一把，形成死锁。它和"锁等待超时"不同——死锁是数据库检测到环后自动回滚一方，锁等待是单纯慢。
- **取证**：`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK` 段，能拿到两个事务各自持锁 / 等锁的 SQL 和等待图，据此还原加锁顺序。
- **根治——固定加锁顺序**：转账前按 `account_id` 排序，无论方向都从小到大依次加锁，所有人都同一顺序就无解环。这是比"加重试"更根本的手段。
- **缩小事务**：把查询、非关键操作移出事务，缩短持锁时间，降低两事务重叠窗口。
- **隔离级别**：降到 RC（配合 row 格式 binlog，保证主从一致）可减少间隙锁，降低死锁概率，但业务要能接受不可重复读。
- **重试必须幂等**：死锁是 InnoDB 自动回滚的，业务必须能安全重试——加重试但不解决加锁顺序，还会再死；且重试要带幂等键，避免重复转账。热点账户另走汇总 / 子账户避免单行争用。

**可接受的关键结论**
- 死锁根因是加锁顺序不一致形成环，与锁等待超时不是一回事。
- `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段能看到等待图。
- 根治是按 `account_id` 排序固定加锁顺序，而非只加重试。
- 缩小事务范围、降隔离级别到 RC（配 row binlog）都能降低概率。
- 重试必须幂等；只 try-catch 不解决顺序问题还会再死。

**考察意图**
验证锁与并发正确性意识。L2 分水岭在能否从"加锁顺序"而非"加重试"根治，并理解死锁是数据库自动回滚、业务需幂等重试——能画出等待环、讲清顺序固定化的是 L2+；只说"catch 住重试就行"的，说明没理解死锁是结构性问题而非偶发异常。

**常见错误回答**
- ❌ "死锁就加 try-catch 重试" —— 顺序不解决还会再死；先固定加锁顺序。
- ❌ "用 `SELECT ... FOR UPDATE` 锁全表" —— 锁范围过大并发崩；只锁涉及账户且按 id 排序。
- ❌ "把隔离级别调到串行化" —— 性能腰斩且仍可能死锁；降到 RC 配 row binlog 更实际。
- ❌ "重试不加幂等" —— 重试可能重复转账；必须幂等键。
- ❌ "死锁偶发忽略就行" —— 每天几十次且影响转账，必须根治加锁顺序。

#### 16.8 【连环雪崩】一次由慢 SQL 引发的全站不可用，怎么复盘与加固？
> **难度**：L3 深入 ｜ **考察频次**：高 ｜ **目标能力**：系统性思考 ｜ **标签**：雪崩、复盘、熔断、故障演练

**业务场景与约束**
- **业务现象**：一次运营查询拖垮全站，故障持续 40 分钟、影响 12 万用户，事后需要复盘与加固。
- **量化约束**：故障持续 40 分钟；影响 12 万用户；起因是一条未加索引的运营查询；演化路径为连接池耗尽 → 业务线程全部阻塞 → 上游超时重试放大流量 → 全站不可用。

**渐进式追问**
1. 故障发生后你第一件事做什么，为什么不能先重启？
2. 根因链应该怎么画，只写"数据库慢"够吗？
3. 恢复手段的优先级是什么，扩容在第几位？
4. 改进项怎么写才不是空话，要不要有 owner 和验收标准？
5. 复盘文档应该包含哪几块，时间线怎么还原？
6. 这次是慢 SQL，下次可能是别的，怎么让系统不再被单点拖垮？

**参考答案要点**
- **先保现场再恢复**：第一动作是保留证据——thread dump + heap dump + 监控快照 + GC 日志，再考虑恢复。一上来重启把现场洗掉，复盘就只能靠猜，根因永远查不清。
- **画根因链而非写表象**：慢 SQL（未加索引的运营查询）→ 单条查询长时间占用连接 → 连接池耗尽 → 业务线程阻塞等连接 → 上游超时后重试放大流量 → 雪崩。要呈现这条因果链，而不是只写"数据库慢"。这是系统性思维的核心。
- **恢复优先级**：先限流 / 降级止血 → 回滚变更（本次是 kill 掉那条运营查询）→ 必要时扩容。注意：上游重试放大时扩容反而喂更多流量，顺序错了越扩越糟。
- **改进项要可执行有 owner**：连接池监控与告警、SQL 上线前执行计划审核、超时与重试预算（上游重试带退避和上限）、熔断、定期压测与故障演练。每条改进必须有负责人和验收标准。
- **复盘文档结构**：时间线 → 影响面 → 根因 → 改进项 → 验收标准。时间线靠监控快照和日志还原，不是凭记忆。
- **防单点**：单点慢查询能拖垮全站，说明缺隔离与熔断。加固方向是资源隔离（连接池按业务分）、熔断、超时预算，让一个慢点无法耗尽全局资源。

**可接受的关键结论**
- 先 dump 保现场（thread/heap/监控/GC 日志）再恢复，重启会洗掉证据。
- 根因要画因果链：慢 SQL → 连接池耗尽 → 线程阻塞 → 重试放大 → 雪崩，而非只写"数据库慢"。
- 恢复优先级：限流降级止血 → 回滚变更 → 最后才扩容（重试放大时扩容反噬）。
- 改进项必须可执行、有 owner、有验收标准，"以后注意"不是改进项。
- 系统级加固靠资源隔离 + 熔断 + 超时预算 + 压测演练，避免单点拖垮全局。

**考察意图**
验证系统性复盘与加固能力。L3 分水岭在能否画出完整根因链、改进项是否可执行且有 owner——能区分"止血动作"和"根治动作"、把故障归因到架构缺失的是 L3；只说"以后注意 SQL 性能""加机器"的是 L2。前者展现对系统韧性的整体思考，后者停留在单点救火。

**常见错误回答**
- ❌ "一上来先重启恢复" —— 重启洗掉所有现场，复盘靠猜；先 dump 再恢复。
- ❌ "根因就是数据库慢" —— 只写表象不画根因链；要慢 SQL→连接池→线程→重试放大。
- ❌ "改进项写'以后注意 SQL 性能'" —— 无可验收动作和 owner；要具体 + 负责人 + 验收。
- ❌ "加机器防雪崩" —— 重试放大时扩容反而更糟；先限流熔断止血。
- ❌ "复盘文档只写结论" —— 缺时间线 / 影响面 / 验收；按固定结构写全。
