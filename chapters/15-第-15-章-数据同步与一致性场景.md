#### 15.1 【缓存一致性】更新 DB 之后删缓存还是更新缓存？并发下还有没有坑？
> **难度**：L2 进阶 ｜ **考察频次**：高 ｜ **目标能力**：边界分析 ｜ **标签**：缓存一致性、Cache Aside

**业务场景与约束**
- **业务背景**：商品详情页是电商核心读链路，日均被访问数亿次；前端和 App 都依赖缓存降低 DB 压力；一旦返回长期脏数据，用户会看到错误价格与下架商品，引发客诉与资损。
- **量化约束**：商品详情读 `8 万 QPS`、写 `200 TPS`、允许 `1 秒`内短暂不一致、不允许出现长期脏数据（脏数据存活超过 1 秒即算缺陷）。

**渐进式追问**
1. 更新数据时，应该先动 DB 还是先动缓存，为什么？
2. 为什么标准做法选"更新 DB 后删缓存"而不是"更新缓存"？
3. 并发下"读未命中 → 读到旧 DB 值 → 才回写缓存"这个脏回写窗口，到底在什么条件下才会真正发生？
4. 这个脏窗口发生的概率有多大，能不能用数字说明它几乎可忽略？
5. 删除缓存这一步如果失败（Redis 抖动/超时），怎么补？
6. 延迟双删能不能彻底解决这个窗口，它又引入了什么问题？
7. 最后能不能加一层兜底，让任何残留脏数据都能自愈？

**参考答案要点**
采用 Cache Aside（旁路缓存）标准顺序：**先更新 DB，再删除缓存**。原因：更新缓存需重新计算（可能要查多张表聚合），成本高且并发写时容易"后到的旧值覆盖先到的新值"；而删缓存是 `O(1)` 幂等操作，下次读自然回填最新值。

```java
// Cache Aside：先更 DB，再删缓存（删除失败进 MQ 重试 / 订阅 binlog 补偿）
orderMapper.update(order);
try { redis.del("order:" + id); }
catch (Exception e) { mq.publish("cache:del", "order:" + id); }
```

脏回写窗口确实存在：线程 A 读未命中 → 读 DB 拿旧值 → 正要写回时，线程 B 完成"更新 DB + 删缓存"，A 才把旧值写回，造成脏数据。但**触发条件极苛刻**：必须 A 的读恰好未命中（高命中率下概率极低），且 A 读 DB 与写缓存之间，B 的整个"更新 + 删缓存"必须紧凑插入。按 `8 万 QPS`、`200 TPS`，读未命中率约 `0.5%`，单次读内发生交错的概率约 `200/80000 × 交错占比`，量级在十万分之一以下，且脏数据最多存活 1 秒。删缓存失败用**重试兜底**：本地记失败日志走 MQ 重试，或订阅 `binlog`（Canal）做删除补偿。延迟双删（更新后删一次、延迟几百毫秒再删）能压低窗口但**不能根除**，还增加无效删除与延迟，仅适合强一致诉求。最后用**缓存 TTL 兜底**（如 `300 秒`），任何残留脏数据都会到期自愈。

**可接受的关键结论**
- 标准顺序固定为"先更新 DB，再删除缓存"，原因不是玄学而是成本与幂等。
- 脏回写窗口只在"读未命中 + 并发写紧凑插入"时触发，量级极低，可量化说明。
- 删除失败必须补偿（MQ 重试 / 订阅 binlog），否则缓存永脏。
- 延迟双删不根除问题且引入额外延迟，仅在强一致诉求下使用。
- 缓存 TTL 是最后兜底，保证任何脏数据都能自愈。

**考察意图**
考察边界分析能力：是否停留在"先删还是后删"的口号，还是能说清脏窗口的**触发条件与概率量级**。区分 L2 与 L3 的分水岭在于：能否用数字说明该窗口"几乎可忽略 + TTL 自愈"，而非空谈"可能不一致"。

**常见错误回答**
- ❌ "先删缓存再更新 DB，这样最安全" —— 错在删除后、DB 提交前若有读请求，会回填旧值且脏数据直到 TTL 才消失；正确做法是先更 DB 后删缓存。
- ❌ "更新缓存比删缓存更实时" —— 错在忽略计算成本与并发写覆盖，且删缓存天然幂等；正确做法是删缓存靠回源回填。
- ❌ "并发下一定会出现脏数据" —— 错在没说明窗口触发条件与概率；正确做法是给出发生条件与量级并用 TTL 兜底。
- ❌ "用分布式锁包住读写保证强一致" —— 错在牺牲读性能（8 万 QPS 会阻塞），正确做法是接受秒级最终一致 + 兜底而非强一致。
- ❌ "删缓存失败无所谓，下次 TTL 会清" —— 错在 TTL 期间可能多次读到脏值；正确做法是失败即补偿删除。

#### 15.2 【缓存异常】大促零点缓存集体失效 + 一个热点 key 被打爆
> **难度**：L2 进阶 ｜ **考察频次**：高 ｜ **目标能力**：组合防御 ｜ **标签**：缓存穿透、击穿、雪崩、热点 key

**业务场景与约束**
- **业务背景**：大促零点大量商品缓存集中过期或集群刚重启，瞬时流量洪峰打向 DB；同时某爆款单品成为超级热点，单 key 流量远超单分片承载，处理不当会连锁拖垮整条读链路。
- **量化约束**：预热 key `300 万`个、热点单 key `20 万 QPS`、Redis Cluster `32 分片`、不允许 DB 被打穿（DB 最大承接应 `5000 QPS`）。

**渐进式追问**
1. 大量 key 同时失效导致请求穿透到 DB，这属于穿透、击穿还是雪崩，三者区别是什么？
2. 针对"穿透"（查不存在的数据），怎么防？
3. 针对"击穿"（单热点 key 失效瞬间海量请求涌向 DB），互斥锁重建、逻辑过期、永不过期三种方案代价分别是什么？
4. 针对"雪崩"（大量 key 同时过期），怎么从 TTL 设计上避免？
5. 单 key 20 万 QPS 远超单分片上限，怎么识别并打散热点 key？
6. 本地缓存（Caffeine）在这一层能挡掉多少流量，又会带来什么一致性问题？
7. 多级缓存 + 熔断降级组合后，如何验证 DB 不会被打穿？

**参考答案要点**
先分清三类问题。穿透 = 查不存在的数据，用**布隆过滤器**拦截非法 key，或对空结果缓存短 `TTL`（如 `60 秒`）防重复穿透；注意空值缓存只对"确实不存在"的 key 生效，避免污染。击穿 = 单热点 key 失效瞬间，三种打法：`互斥锁重建`（`SETNX` 抢锁，仅一个线程回源，代价是锁等待与死锁风险）、`逻辑过期`（值里带过期时间、异步重建，代价是短暂返回旧值）、`永不过期 + 异步刷新`（后台定时刷新，代价是内存常驻与更新不及时）。雪崩 = 大量 key 同过期，核心是**TTL 加随机 jitter**（如基础 `300s ± 60s`）打散失效点，配合多级缓存与熔断（DB 承压超阈值即降级返回兜底）。

```java
// 互斥锁重建：仅一个线程回源，其余等待/降级
if (!redis.setnx("lock:" + key, "1", 3, SECONDS)) {
    return getFromLocalCache(key); // 降级取本地旧值
}
try { String val = loadFromDb(key); redis.setex(key, 300, val); }
finally { redis.del("lock:" + key); }
```

热点 key 用 `OBJECT FREQ`（Redis 7.0 起 LFU，替代旧 ziplist 统计）或代理层统计识别，打散为 `key_0..key_31` 分散到 32 个分片，单分片只承接约 `6000 QPS`。再在应用层加 **Caffeine 本地缓存**挡掉 `80%` 以上读（20 万 QPS 落到 Redis 仅约 4 万），代价是本地多实例间短暂不一致，靠短 `TTL`（如 `2 秒`）收敛。最后用熔断（如 Sentinel）在 DB QPS 逼近上限时降级，确保 DB 不被打穿。代价对比：布隆过滤器省内存但有误判；互斥锁保一致但有等待；本地缓存削峰但引入不一致，需按业务取舍。

**可接受的关键结论**
- 穿透、击穿、雪崩是三件事，防御手段不同，不能混为一谈。
- 雪崩靠 TTL 随机 jitter 打散，而非统一过期。
- 热点 key 必须识别后打散到多分片，单实例纵向扩容无效。
- 本地缓存（Caffeine）能削峰但引入多实例不一致，需短 TTL 收敛。
- 熔断降级是最后护栏，确保 DB 不被打穿。

**考察意图**
考察组合防御与权衡：能否把穿透/击穿/雪崩区分清楚并分别选型，而非混用一套方案。分水岭在于能否说出热点 key 必须**打散到多分片**（单分片有上限），以及本地缓存的代价是一致性。

**常见错误回答**
- ❌ "给所有 key 设一样长的 TTL 最省事" —— 错在制造集体失效引发雪崩；正确做法是 TTL 加随机 jitter 打散。
- ❌ "热点 key 直接加更大机器规格顶住" —— 错在单 key 受限于单分片/单线程，纵向扩容无效；正确做法是 key 打散到多分片。
- ❌ "穿透用缓存 null 就行，不用布隆过滤器" —— 错在恶意遍历不存在的 key 仍会击穿（null 也占内存）；正确做法是布隆过滤器前置拦截。
- ❌ "本地缓存能彻底解决热点" —— 错在忽略多实例不一致与内存放大；正确做法是用短 TTL 收敛并配合 Redis 双层。
- ❌ "互斥锁重建永远不会出问题" —— 错在锁未设超时会导致死锁、线程堆积；正确做法是锁带超时 + 看门狗续期。

#### 15.3 【binlog 同步】Canal / Flink CDC 同步到 ES 和数仓
> **难度**：L3 高级 ｜ **考察频次**：中 ｜ **目标能力**：数据管道设计 ｜ **标签**：CDC、Flink、幂等、乱序

**业务场景与约束**
- **业务背景**：主库订单/商品变更需近实时同步到 ES（搜索）和数仓（分析）；下游消费方依赖准确数据做搜索排序与报表，数据错乱会直接导致搜索结果错误与统计失真。
- **量化约束**：主库 `5000 TPS` 写入、同步链路 RT 秒级、ES 索引 `2 亿`文档、允许分钟级最终一致。

**渐进式追问**
1. CDC 链路默认是"至少一次"还是"恰好一次"，为什么不能假设不丢不重？
2. 下游 ES/数仓怎么保证重复消息不写脏，靠去重表还是别的方式？
3. 消息乱序（后发生的变更先到）怎么处理，Flink 里用什么机制？
4. 全量初始化（存量 2 亿）和增量（binlog）怎么平滑切换，切换点会不会丢或重？
5. 上游 DDL（加列/改类型）同步链路怎么兼容与告警？
6. 怎么监控同步延迟，lag 指标怎么取？
7. 怎么证明 ES/数仓和主库最终是一致的，校验手段是什么？

**参考答案要点**
基于 MySQL 8.0（InnoDB、RR 隔离级别、`row` 格式 binlog），CDC 本质是**至少一次**语义（Kafka 4.0 起仅支持 KRaft，producer 重试、consumer 重平衡都可能重投），所以下游必须幂等。正确做法不是建"去重表"，而是**幂等 upsert**：以业务主键（如 `order_id`）做覆盖写，配合**版本号/时间戳比对**（写入时仅当新值更新才覆盖），旧版本迟到直接丢弃。

```sql
-- 幂等 upsert：以业务主键覆盖写（版本比对在应用层判断）
INSERT INTO dw_order(order_id, status, update_time)
VALUES(#{id}, #{status}, #{ts})
ON DUPLICATE KEY UPDATE
  status = VALUES(status), update_time = VALUES(update_time);
```

乱序用 Flink `upsert-kafka` + 按主键分区，保证同主键进同一并行度；用**水位线（watermark）+ 状态 TTL** 做"按主键取最新"：到达的变更若 `update_time` 小于已存值则忽略。全量/增量切换靠**存量快照 + 增量位点**：先记录 binlog 位点 `P`，再导存量（此时新写入已进 binlog 不会丢），导完用 `P` 起增量；重叠窗口用幂等 upsert 消重，保证不丢不重。DDL 变更需链路支持 schema 演进（如 Avro + registry）并告警人工确认，避免字段错位。监控用 Kafka consumer `lag` + Flink `currentWatermark` 反映延迟。校验用 `count`/`sum` 比对 + 抽样 `detail` 比对，定位差异批次。

**可接受的关键结论**
- CDC 默认至少一次，下游必须幂等，靠业务主键 upsert + 版本比对。
- 乱序用按主键分区 + 时间戳比对取最新，不依赖到达顺序。
- 全量/增量切换先记位点再导存量，重叠区靠幂等消重保证不丢不重。
- DDL 需 schema 演进与告警，不能静默兼容。
- 一致性靠 count/sum + 抽样 detail 校验，差异要可定位到批次。

**考察意图**
考察数据管道设计：能否把"至少一次 + 幂等 + 乱序"作为默认前提，而非假设链路可靠。分水岭是能否说清全量/增量切换的位点机制，以及用幂等 upsert 而非去重表。

**常见错误回答**
- ❌ "CDC 是恰好一次，不用管重复" —— 错在 Kafka/Canal 默认至少一次，重投必然发生；正确做法是下游幂等 upsert。
- ❌ "用一张去重表记 messageId 防重" —— 错在去重表自身有 TTL/容量问题且无法处理乱序覆盖；正确做法是用主键做幂等覆盖写。
- ❌ "乱序就按到达顺序写" —— 错在旧值会覆盖新值；正确做法是按 `update_time`/`版本号` 比对取最新。
- ❌ "全量导完直接切增量，中间空窗会丢" —— 错在没先记位点再导存量；正确做法是先位点后存量，重叠区靠幂等消重。
- ❌ "DDL 变更同步链路自动兼容不用担心" —— 错在字段类型/顺序变化会错位甚至写崩；正确做法是 schema 演进 + 告警。

#### 15.4 【不停机迁移】单表 8 亿行拆成 64 张分表
> **难度**：L3 高级 ｜ **考察频次**：中 ｜ **目标能力**：迁移方案 ｜ **标签**：分表、双写、灰度切流、回滚

**业务场景与约束**
- **业务背景**：单表 8 亿行已成性能瓶颈，慢查询频发拖垮整体 RT；需水平拆成 64 张分表，但迁移期间业务不能停，且一旦出问题必须能秒级回滚，否则就是线上事故。
- **量化约束**：`8 亿`行、日均写入 `2000 万`、允许秒级只读窗口、必须可回滚、不能丢数据。

**渐进式追问**
1. 迁移核心思路是双写还是全量拷贝后切换，为什么选双写？
2. 双写时新旧表都写，如果写新表失败怎么办，怎么降级？
3. 8 亿存量怎么搬，怎么限速避免打爆主库，断了怎么续？
4. 怎么证明新表和旧表数据一致？
5. 切流怎么灰度，从哪类流量开始？
6. 出问题怎么回滚，回滚是切回去还是反向双写？
7. 分片键怎么选，选错会有什么后果？

**参考答案要点**
核心是**双写 + 灰度切读**：通过开关同时写新旧表，校验一致后逐步把读切到新表。双写失败不能影响主流程——写新表失败应**降级为记补偿日志/MQ**，旧表仍正常，保证不丢；等新表恢复后由补偿任务补齐。存量迁移按**主键分批**（如每批 `1 万`行）限速（如每秒 `500` 批）迁移，避免压垮主库；用游标推进，断点续跑只需记录 `last_id`。

```sql
-- 分批迁移游标，断点续跑靠 last_id
INSERT INTO order_new_${shard}(id, user_id, amount, update_time)
SELECT id, user_id, amount, update_time FROM order_old
WHERE id > #{lastId} ORDER BY id LIMIT 10000;
```

校验做**全量 checksum**（按主键区间分片，`count` + `sum(关键数值列)` + `max(update_time)` 比对）+ 抽样逐行比对 + 实时增量比对（双写期间新旧差异应趋近于 0）。切流灰度：先放**白名单用户**读新表 → 观察无异常 → 放 `1%` 流量 → 全量切读新表 → 最后停写旧表。回滚用**反向双写**（新表变更同步回旧表）+ 切回读旧表，因为旧表数据一直被双写保持最新，所以回滚是秒级的。分片键必须**贴合查询模式**（如按 `user_id` 分片，则按用户查都落单表）；选错（如按无意义 `id` 但业务都按 `order_no` 查）会导致跨 64 片广播查询，比单表还慢。分布式 ID 用雪花或号段，避免自增冲突与热点。

**可接受的关键结论**
- 迁移用双写 + 灰度切读，开关控制，绝不一次性切换。
- 双写失败降级为补偿日志，保证主流程不丢数据。
- 存量迁移按主键分批限速 + 断点续跑，避免打爆主库。
- 校验靠全量 checksum + 抽样 + 实时增量，不能只看 count。
- 回滚靠反向双写 + 切读旧表，因为旧表一直被保持最新。

**考察意图**
考察迁移方案的工程稳健性：能否把"可回滚""不丢数据"作为一等约束。分水岭是能否讲清双写失败降级与反向双写回滚，而非只想"切过去"。

**常见错误回答**
- ❌ "直接 rename 新表上线最快" —— 错在一旦新表有问题无法回滚且停写期间丢数据；正确做法是双写 + 灰度切流。
- ❌ "存量一次性全量迁移" —— 错在打爆主库引发线上故障；正确做法是主键分批 + 限速 + 断点续跑。
- ❌ "校验只比对行数 count" —— 错在一多一少互相抵消；正确做法是 checksum + 抽样 detail 比对。
- ❌ "分片键随便选一个均匀的字段" —— 错在忽略查询模式导致跨片广播；正确做法是贴合高频查询维度。
- ❌ "停写旧表后再发现数据不对就完了" —— 错在没保留反向双写兜底；正确做法是回滚靠反向双写 + 切读。

#### 15.5 【缓存预热与热点发现】大促前 30 分钟怎么预热？
> **难度**：L1 基础 ｜ **考察频次**：中 ｜ **目标能力**：工程落地 ｜ **标签**：缓存预热、热点探测、本地缓存

**业务场景与约束**
- **业务背景**：大促前若不预热，零点流量会瞬间击穿缓存打向 DB；运营也会圈定一批必抢商品。这是一道偏工程落地的题，重点是把"别把 DB 打爆"这个常识变成可执行的步骤。
- **量化约束**：`300 万`商品、预热窗口 `30 分钟`、Redis 内存 `64G`、预热过程本身不能打爆 DB。

**渐进式追问**
1. 怎么知道哪些商品需要预热，数据是哪来的？
2. 预热时一次性把所有 key 灌进 Redis 会不会有问题？
3. 怎么给预热限速，避免把 DB 打爆？
4. 大促进行中怎么发现"正在变热"的新热点？
5. 本地缓存（Caffeine）在这一层起什么作用？
6. 预热失败或 Redis 内存不够怎么办，怎么兜底？

**参考答案要点**
预热名单来自三个来源：**离线挖掘**（历史 PV 高的商品 + 加购/收藏 TopN）、**运营清单**（大促主推坑位）、实时兜底。拿到名单后**不能一把全灌**，否则瞬时高并发回源会打爆 DB。正确做法是**限速预热**：用令牌桶（如每实例每秒 `500` 个 key）分批从 DB 读取并写入 Redis，`30 分钟`窗口足够平滑铺完 300 万 key（500 × 1800s = 90 万/实例，多实例并行即可）。

```java
// 令牌桶限速预热，避免打爆 DB
RateLimiter limiter = RateLimiter.create(500); // 500 key/s/实例
for (String key : hotKeys) {
    limiter.acquire();
    redis.setex(key, ttl, loadFromDb(key));
}
```

大促中热点靠**实时探测**：客户端/网关上报访问计数，或利用 Redis 7.0 的 LFU（`OBJECT FREQ`）识别高频 key，命中后自动加载到**本地缓存 Caffeine** 挡一层，减少 Redis 网络往返。内存方面，Redis `maxmemory-policy` 选 `allkeys-lru`（允许所有 key 被淘汰，内存满时自动回收冷 key），避免 `volatile-lru` 因未设 TTL 的 key 无法淘汰而 OOM。要注意 big key（如超长 value）会阻塞单线程，预热时拆分。兜底：**熔断 + 限流降级到 DB**，但 DB 侧必须有限流（如信号量），防止预热/突发把 DB 打穿；预热失败不影响线上已缓存数据。

**可接受的关键结论**
- 预热名单 = 离线挖掘 + 运营清单 + 实时兜底，三源合流。
- 预热必须限速（令牌桶 + 分批），绝不能一把灌爆 DB。
- 实时热点靠客户端上报或 Redis LFU（`OBJECT FREQ`）探测。
- 内存淘汰选 `allkeys-lru`，避免冷 key 无法回收导致 OOM。
- 兜底用熔断 + DB 侧限流，预热失败不影响已缓存数据。

**考察意图**
考察工程落地基本功：能否把"预热不能打爆 DB"作为铁律，并用限速/探测/淘汰策略/兜底四件套落地。这是本章唯一的 L1 锚点，分水岭是能否讲清限速与 `allkeys-lru` 的选择理由。

**常见错误回答**
- ❌ "大促前把所有商品一次性全量预热" —— 错在瞬时回源打爆 DB；正确做法是令牌桶限速分批预热。
- ❌ "热点只靠预热名单，不实时探测" —— 错在漏掉临时爆款；正确做法是离线名单 + 实时 LFU 探测双轨。
- ❌ "Redis 内存满了就加机器" —— 错在没设淘汰策略导致 OOM；正确做法是配 `allkeys-lru` 自动回收冷 key。
- ❌ "本地缓存 Caffeine 不需要过期" —— 错在多实例间数据变更无法感知，长期不一致；正确做法是短 TTL 定期刷新。
- ❌ "预热失败就重试不限速" —— 错在重试风暴二次打爆 DB；正确做法是限流 + 熔断降级。

#### 15.6 【一致性校验】怎么证明两个异构数据源是一致的？
> **难度**：L3 高级 ｜ **考察频次**：中 ｜ **目标能力**：验证设计 ｜ **标签**：数据校验、checksum、对账

**业务场景与约束**
- **业务背景**：MySQL 主库 8 亿行与数仓需定期核对一致；资损排查与合规审计都要求"能证明没丢没重"，且差异要能定位到具体行，否则对账报告无人敢签字。
- **量化约束**：MySQL `8 亿`行 vs 数仓、不能全表锁、每天跑一次、差异必须可定位到具体行。

**渐进式追问**
1. 只比对两边的 count 总行数够不够证明一致？
2. 海量数据怎么分批做校验而不锁全表？
3. 为什么会有"假差异"，怎么排除？
4. checksum 只定位到批次还不够，怎么进一步定位到具体行？
5. 偶发抖动导致的差异怎么避免误报？
6. 校验任务本身不能影响线上，怎么隔离资源？
7. 校验结果给人看要长什么样？

**参考答案要点**
只比对 `count` **远远不够**：少一行又多一行会互相抵消，两边 count 相等但数据已错。正确做法是**分批 checksum**：按主键区间或时间分片（如每 `100 万`行一批），每批比对 `count`、`sum(关键数值列)`、`max(update_time)`。这样差异能**定位到具体批次**而非全表。全程走**覆盖索引/分批 `WHERE id BETWEEN ? AND ?`**，不锁全表，对线上无感。

```sql
-- 分批 checksum：每批比对 行数/数值和/最大更新时间
SELECT COUNT(*), SUM(amount), MAX(update_time)
FROM orders
WHERE id BETWEEN #{start} AND #{end}
  AND update_time < NOW() - INTERVAL 5 MINUTE;
```

"假差异"来自**同步延迟窗口**：校验瞬间主库有在途未同步到数仓的变更，会造成批次不一致。必须设**延迟窗口**（如仅比对 `update_time < 当前时间 - 5 分钟` 的冷数据），热数据留给下次。定位到批次后做**抽样 detail 比对**（逐行 `SELECT` 关键字段），精确定位到具体行。为避免偶发抖动误报，差异要做**二次复检**（隔几分钟重跑该批次），确认仍不一致才落表。差异落`差异表`并触发**自动补偿**（重跑该批同步）。资源隔离：校验任务走**只读从库 / 低优先级队列**，限流扫描，监控其对主库 QPS 的影响。对账报告要给人看：含批次、差异行数、样例主键、成因假设，便于人工确认。

**可接受的关键结论**
- count 相等不可信，必须分批 checksum（count+sum+max(update_time)）。
- 分批走覆盖索引不锁全表，对线上无感。
- 必须排除同步延迟窗口的假差异，否则全是误报。
- 差异经二次复检后落表并自动补偿，形成闭环。
- 校验任务需资源隔离 + 限流，对账报告要能给人看。

**考察意图**
考察验证设计思维：能否把"证明一致"当作可量化、可定位、可闭环的工程问题。分水岭是能否指出 `count` 抵消陷阱与延迟窗口假差异，而非只说"跑个脚本比对"。

**常见错误回答**
- ❌ "count 相等就说明一致" —— 错在一多一少抵消；正确做法是分批 checksum + 抽样 detail。
- ❌ "全表锁住再比对最准" —— 错在 8 亿行锁表会拖垮线上；正确做法是分批覆盖索引扫描不锁全表。
- ❌ "出现差异立刻告警人工处理" —— 错在没排除延迟窗口假差异与偶发抖动；正确做法是延迟窗口 + 二次复检。
- ❌ "校验在凌晨随便跑无所谓" —— 错在仍可能打爆从库/主库；正确做法是资源隔离 + 限流。
- ❌ "差异只记日志不补偿" —— 错在只发现问题不闭环；正确做法是差异落表 + 自动补偿。

#### 15.7 【幂等方案】Token 预领取、唯一索引、状态机，边界在哪？
> **难度**：L2 进阶 ｜ **考察频次**：高 ｜ **目标能力**：方案边界 ｜ **标签**：幂等、Token、唯一索引、状态机

**业务场景与约束**
- **业务背景**：支付/下单类写接口会被网关重试、MQ 重投，重复请求若不加防护会造成重复扣款/重复下单。需清楚三种幂等手段各自的边界，避免只知其一。
- **量化约束**：写接口 `3000 TPS`、需支持网关重试与 MQ 重投、存储 MySQL + Redis。

**渐进式追问**
1. 幂等靠"前端拦住重复点击"够吗，为什么不够？
2. Token 预领取方案怎么实现，天然有什么代价？
3. 删除已用 token 时，为什么必须 `DEL` 原子操作而不是先查后删？
4. 唯一索引方案为什么最可靠，怎么正确识别冲突？
5. 状态机 CAS 适合什么场景，怎么判断成功？
6. 三者组合时推荐姿势是什么？
7. 幂等键怎么设计，幂等和并发安全是一回事吗？

**参考答案要点**
幂等不能只靠前端——网关重试、MQ 重投都在网络层，前端拦不住。三种手段边界不同：**Token 预领取**：业务前先向 Redis 申请 `token`（如 `SET token uuid EX 300`），提交时携带，服务端 `DEL` 成功才处理；代价是多一次 RT，且 token 需设过期防堆积。**关键坑**：删除必须用原子 `DEL`，若"先 `GET` 判断存在 → 再 `DEL`"在并发下两个请求都可能通过，失去防重意义。

```sql
-- 状态机 CAS：看影响行数判断是否推进
UPDATE `order` SET status = 'PAID'
WHERE id = #{id} AND status = 'UNPAID';
-- affected rows = 0 表示已被其他请求处理，视为幂等
```

**唯一索引**最可靠：在表上建 `(biz_id, scene)` 唯一键，重复插入直接抛 `DuplicateKeyException`，捕获后即视为幂等成功而非系统错误——很多人错把它当异常抛出去。**状态机 CAS**适合有明确状态流转（如 `待支付→已支付`）：`UPDATE ... WHERE status = ?`，看**影响行数**判断（0 行说明已被他人处理）。推荐姿势：**Token 防重复提交（挡掉用户层重复）+ 唯一索引兜底（挡掉所有层重复）+ 状态机防乱序（保证状态只前进不回退）**。幂等键设计：`业务主键 + 场景 + 时间窗`（如 `order_123_pay_20260913`），过期清理防重表膨胀。**重要区分**：幂等 ≠ 并发安全，幂等解决"重复执行结果一致"，并发安全还要靠锁/原子操作解决"同时执行"的问题。

**可接受的关键结论**
- 幂等必须在服务端做，前端禁用按钮挡不住网关/MQ 层重试。
- Token 删除用原子 `DEL`，先查后删在并发下会失效。
- 唯一索引最可靠，冲突要捕获 `DuplicateKeyException` 而非当错误抛。
- 推荐组合：Token 防重提交 + 唯一索引兜底 + 状态机防乱序。
- 幂等 ≠ 并发安全，两者需分别处理。

**考察意图**
考察方案边界认知：能否分清三种幂等手段的适用面与代价，而非只会用一种。分水岭是能否点出"幂等 ≠ 并发安全"以及 Token 删除必须原子 `DEL`。

**常见错误回答**
- ❌ "前端禁用按钮就能幂等" —— 错在网关重试与 MQ 重投绕过了前端；正确做法是服务端幂等。
- ❌ "删除 token 用先查后删更安全" —— 错在并发下两个请求都能通过检查；正确做法是原子 `DEL`。
- ❌ "唯一索引冲突就当系统错误抛异常" —— 错在把幂等成功当成故障；正确做法是捕获 `DuplicateKeyException` 视为重复提交成功。
- ❌ "用了幂等就不需要并发控制了" —— 错在幂等不解决同时执行的竞态；正确做法是幂等 + 锁/原子操作各管一段。
- ❌ "状态机 CAS 看返回值布尔就行" —— 错在应看影响行数判断状态是否真的被推进；正确做法是 `WHERE status=?` 后检查 affected rows。

## 如何用好这一模块：场景题答题方法论

> 场景题和八股题的评分逻辑完全不同。八股题考"你知不知道"，场景题考"你在不确定里怎么决策"。

### 场景题 vs 八股题：面试官到底在评什么

八股题你背熟就能拿分，场景题背不到——它会不断给你加压、改条件、逼你承认代价。下面这张表先把评分逻辑摆清楚，你才知道力气该往哪使。

| 维度 | 八股题 | 场景题 |
| --- | --- | --- |
| 考察目标 | 知不知道某个知识点 | 在不确定和约束里怎么决策 |
| 答错的后果 | 暴露知识盲区，扣分项明确 | 暴露思维方式和工程成熟度 |
| 是否可以背 | 大量可背 | 背不到，追问即穿帮 |
| 追问的作用 | 验证记忆深度 | 验证边界、权衡、诚实度 |
| 得分天花板 | 答对即满分 | 没有满分，权衡讲得好才高分 |

结论：八股题是"会不会"，场景题是"靠不靠谱"。面试官宁可要一个能把 80 分方案讲清楚、兜底想周全的人，也不要一个背得出最优架构但一被追问就卡壳的人。

### 答题四步法

每次开口，按这个顺序走，能覆盖绝大多数场景题的得分点。

① **复述约束**：开口先把量级、数据规模、一致性要求复述一遍，并主动追问缺失的约束。例如"这个接口允许少卖吗""能接受多久的数据不一致""峰值 QPS 大概多少"。主动追问本身就算加分——它证明你在定义问题，而不是急着给答案。
② **给主方案**：先给一个今天就能落地的 80 分方案，不要一上来堆"最终一致性 + 分库分表 + 多活"的最优架构。能上线的方案比完美的 PPT 值钱。
③ **讲权衡**：明确说出你放弃了什么、代价是什么。是放弃了一致性换延迟，还是放弃了简单性换来扩展性？说不出代价的方案，面试官默认你没想清楚。
④ **补兜底**：失败了怎么办、怎么发现、怎么补偿、怎么回滚。主链路讲完不讲兜底，等于只做了上半场。

### 面试官追问的四种动机

追问不是为难你，是有明确目的。看清动机，才知道往哪个方向接。

| 动机 | 典型问法 | 你应该怎么接 |
| --- | --- | --- |
| 验证深度 | "你说的这个参数具体生效机制是什么？" | 往细节钻，给出参数名、命令、具体指标，别用"大概""应该"糊弄 |
| 验证边界 | "如果流量翻 10 倍 / 发生网络分区呢？" | 承认条件变化，重新评估方案，展示条件敏感度 |
| 验证权衡 | "你这么做放弃了什么？" | 主动说出代价，展示取舍意识，而不是说"没有缺点" |
| 验证诚实度 | "这个你实际线上做过吗？" | 没做过就明说，讲清你会怎么验证，绝不硬编 |

### 常见失分点 TOP 8

1. **上来就说"用 Redis 分布式锁"，但不说锁粒度、超时、失败重试** —— 失分：方案不可落地，像背过名词。怎么改：先说锁的是哪个资源、粒径多大、拿不到锁怎么办、过期了任务还没跑完怎么办。
2. **说"最终一致"却说不出对账和补偿怎么落地** —— 失分：只抛概念没工程细节。怎么改：讲对账任务频率、差异怎么发现、补偿如何保证幂等。
3. **方案里全是"高性能""高可用"这种无数字的形容词** —— 失分：无法判断量级与可行性。怎么改：给 QPS、数据量、RT 目标、可容忍丢失量等具体数字。
4. **一上来堆最优架构，不做 80 分方案** —— 失分：落地性差、不务实。怎么改：先给能今天上线的方案，再谈演进路径。
5. **不主动追问缺失约束** —— 失分：遗漏关键边界条件。怎么改：开口先复述约束并追问"允许少卖吗""能接受多久不一致"。
6. **只讲主链路不补兜底** —— 失分：没考虑失败与回滚。怎么改：讲失败怎么发现、怎么补偿、怎么回滚。
7. **被追问边界就改口或硬编没做过的** —— 失分：暴露不诚实或不严谨。怎么改：承认没做过，讲清楚验证路径。
8. **给的方案无法排查、没有埋点和指标** —— 失分：线上不可观测。怎么改：设计阶段就带监控、`traceId`、告警阈值。

### 怎么用这一模块自测

1. **遮住答案先自己答**：按四步法完整走一遍，别急着看参考答案。
2. **对照"可接受的关键结论"逐条打分**：缺一条扣一分，低于 3 条说明没答到点上。
3. **"渐进式追问"要逐条口头答一遍**，而不是看一遍——真实面试里追问才是分水岭，眼看和嘴答是两回事。
4. **答完反问自己**：我的方案有数字吗？有兜底吗？能排查吗？三项都"有"才算过关。
5. **同一题隔一周再答一次**：看权衡是否讲得越来越清楚，这才是能力增长。
